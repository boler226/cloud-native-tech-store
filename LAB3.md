# Лабораторна робота 3. Конкурентний pipeline обробки даних у Go

Консольний застосунок `go-pipeline/` обробляє набір числових задач у конкурентному режимі:

```
Producer ──► jobs ──► Worker Pool (1/2/4/8/16) ──► results ──► Aggregator ──► Output
             chan Job        N × worker()              chan Result
```

| Компонент | Файл | Що робить |
|---|---|---|
| Producer | `internal/pipeline/producer.go` | Створює `Tasks` задач `Job{ID, Value}`, пише в `jobs`, після завершення **закриває** `jobs` |
| Worker | `internal/pipeline/worker.go` | Читає з `jobs`, обчислює, пише `Result{JobID, Value}` у `results`; завершується, коли `jobs` закрито або `ctx.Done()` |
| Aggregator | `internal/pipeline/aggregator.go` | Читає `results`: рахує завершені задачі, накопичує суму, виявляє дублі, фіксує час завершення |
| Оркестрація | `internal/pipeline/pipeline.go` | Створює канали, запускає Producer + воркерів, `WaitGroup` + закриття `results`, `context` |
| Обчислення | `internal/pipeline/compute.go` | `value*value` (+ опційна "складність" через `-work`) |
| Серія запусків | `internal/bench/bench.go` | Перебір комбінацій параметрів, медіана, Markdown-таблиця |
| CLI | `main.go` | Прапорці, Ctrl+C / `-timeout` → скасування контексту |

## Як це влаштовано

**Закриття каналів без гонок і витоків.** Кожен канал закриває рівно один власник:
`jobs` закриває Producer (`defer close(jobs)`), а `results` — окрема горутина після
`wg.Wait()`, тобто коли **всі** воркери завершились. Тому Aggregator може просто робити
`for r := range results`, а воркери ніколи не пишуть у закритий канал.

**Скасування (`context` + `select`).** Обидві блокуючі операції воркера — читання задачі та
запис результату — обгорнуті в `select` з `ctx.Done()`. Те саме в Producer. Завдяки цьому
при Ctrl+C чи `-timeout` жодна горутина не "застрягає" на каналі, і `Run` повертається,
лише коли всі горутини завершились (це перевіряє тест `TestRunCancellation`).

**Buffer.** Параметр `-buffer` задає ємність **обох** каналів (`jobs` і `results`):
`0` — unbuffered (кожна передача — "рукостискання" між горутинами), `10/100/1000` — buffered.

**Складність обчислення (`-work`).** При `-work=0` задача — це лише `value*value`, тобто
кілька наносекунд: тоді вимірюється переважно вартість передачі через канали, а не обчислення.
При `-work=N` після піднесення до квадрата виконується N ітерацій лінійного конгруентного
генератора — "складніше" обчислення, на якому розпаралелення воркерів стає помітним.
За замовчуванням `-work=1000`.

**Перевірка коректності.** Після кожного запуску сума результатів звіряється з еталоном,
порахованим послідовно (без горутин; час еталона не входить у `Time`). Також Aggregator
виявляє дублі й "чужі" `JobID`. Тобто таблиця часу завжди підкріплена перевіркою, що
конкурентна версія дає той самий результат.

## Запуск

Потрібен Go 1.22+. Усі команди — з папки `go-pipeline`.

```powershell
cd go-pipeline

# один запуск
go run main.go -tasks=10000 -workers=4 -buffer=100

# те саме з перевіркою синхронізації (race detector), як вимагає завдання
go run -race main.go -tasks=10000 -workers=4 -buffer=100

# unit-тести (усі комбінації workers × buffer, скасування, відсутність витоку горутин)
go test -race ./...

# демонстрація скасування контексту: обробку буде перервано через 100мс
go run main.go -tasks=100000000 -workers=8 -buffer=10 -timeout=100ms
```

Прапорці одного запуску:

| Прапорець | За замовч. | Опис |
|---|---|---|
| `-tasks` | 10000 | Кількість задач (100, 1000, 10000, 100000, …) |
| `-workers` | 4 | Кількість воркерів (1, 2, 4, 8, 16, …) |
| `-buffer` | 0 | Ємність каналів (0, 10, 100, 1000, …) |
| `-work` | 1000 | Складність обчислення однієї задачі (0 = лише `value*value`) |
| `-timeout` | 0 | Скасувати через цей час, напр. `50ms` (0 = без ліміту) |
| `-verify` | true | Звіряти підсумок з еталоном |

> **`-race` на Windows.** Race detector потребує cgo і C-компілятора. Якщо `go run -race`
> скаржиться на `cgo` / `gcc`, встановіть MinGW-w64 (наприклад, через MSYS2 або
> `winget install BrechtSanders.WinLibs.POSIX.UCRT`), додайте `gcc` у `PATH` і виставте
> `$env:CGO_ENABLED = "1"`. З `-race` програма працює в кілька разів повільніше —
> **не знімайте з ним таблицю часу**, використовуйте його лише для перевірки синхронізації.

## Серія запусків і таблиця

Режим `-bench` перебирає всі комбінації й друкує Markdown-таблицю. Кожна комбінація
запускається `-repeat` разів (за замовч. 5), у таблицю йде **медіана**; перед серією
виконується один прогрівальний запуск. Колонка `Speedup` — прискорення відносно 1 воркера
з тим самим `Tasks` і `Buffer`.

```powershell
# повна матриця: workers 1,2,4,8,16 × buffer 0,10,100,1000 для 10000 задач
go run main.go -bench

# рівно ті комбінації, що в завданні
go run main.go -bench -workers-list=1,2,4,8 -buffers-list=0
go run main.go -bench -workers-list=4,8 -buffers-list=100

# різна кількість задач
go run main.go -bench -tasks-list=100,1000,10000,100000

# лише накладні витрати каналів (без "важкого" обчислення)
go run main.go -bench -work=0
```

Для чесного порівняння закрийте важкі програми (браузер, IDE-індексація) на час вимірів.

### На що звернути увагу в аналізі

- **Масштабування за кількістю воркерів.** Для CPU-навантаження (`-work=1000`) час має
  зменшуватись із ростом воркерів приблизно до кількості фізичних ядер, після чого виграшу
  майже немає (більше воркерів, ніж ядер, лише конкурують за процесор).
- **Вплив буфера.** Unbuffered-канал змушує Producer/воркерів/Aggregator синхронізуватись на
  кожній передачі (багато перемикань горутин); buffered-канали згладжують це й зазвичай
  швидші. Після певної ємності (100 → 1000) подальший виграш мізерний.
- **Накладні витрати каналів (`-work=0`).** Коли обчислення тривіальне, більше воркерів може
  навіть **уповільнити** обробку: канали — спільний ресурс, і боротьба за них коштує дорожче,
  ніж саме `value*value`. Це добре показує, що паралелізм виправданий, лише якщо робота
  на одну задачу достатньо "важка" порівняно з вартістю передачі.
- **Коректність.** Усі запуски проходять перевірку суми й відсутності дублів; `go run -race`
  не повідомляє про data race — це підтверджує правильність синхронізації
  (`WaitGroup`, закриття каналів, `context`).
