# Лабораторна робота 2. Моделі конкурентності та планування обчислень у Node.js та Go

Продовження [лабораторної 1](README.md). До обох сервісів додано два нові ендпойнти:

| Метод | Шлях | Опис |
|---|---|---|
| GET | `/io` | Асинхронне очікування (`?delayMs=`, за замовч. 200) |
| GET | `/cpu` | **Node.js:** синхронний важкий цикл (`?iterations=`) |
| GET | `/cpu/sequential` | **Go:** декілька важких проходів ОДИН ЗА ОДНИМ у тій самій горутині (`?iterations=&passes=`) |
| GET | `/cpu/parallel` | **Go:** та сама сумарна робота, але кожен прохід — окрема goroutine |

Навантаження в `/cpu*` — проста лічилка (`counter++` у циклі), щоб виключити побічні ефекти
(алокації, I/O) і виміряти саме процесорний час.

## 1. Ідея експерименту

**Node.js** — однопотоковий event loop. Асинхронний I/O (таймери, мережа, файли) не займає
головний потік — поки `/io` "чекає", Node вільно обробляє інші запити. А **синхронний** код
(наш `/cpu`) виконується в тому самому головному потоці й блокує його повністю: жоден інший
запит (навіть `/health`) не отримає відповіді, доки цикл не завершиться.

**Go** — модель M:N-планування: кожен HTTP-запит обробляється в окремій **goroutine** (легкий
потік виконання рантайму), яких можуть бути тисячі, і рантайм розподіляє їх по доступних
OS-потоках/ядрах. `time.Sleep` паркує горутину, не займаючи OS-потік. А для CPU-задач з
Go 1.14 рантайм має **асинхронне витіснення** (async preemption): навіть "тугий" цикл без
викликів функцій періодично перериває сигналом, щоб дати шанс іншим горутинам. Якщо ядер
кілька, `/cpu/sequential` і `/cpu/parallel` виконують однаковий обсяг роботи, але
`/cpu/parallel` розподіляє її по різних ядрах одночасно — і завершується швидше.

## 2. Як самостійно провести обидва тести

### Крок 1. Дослід "спочатку `/cpu`, потім кілька `/health`"

Скрипт `scripts/blocking-demo.mjs` **не піднімає сервер сам** — потрібно запустити його вручну
в одному терміналі, а сам скрипт — в іншому.

**Node:**
```powershell
# Термінал 1
cd node-service
npm start
```
```powershell
# Термінал 2
cd scripts
node blocking-demo.mjs http://localhost:3000 /cpu
```

**Go** (зупиніть Node у терміналі 1 через `Ctrl+C`, запустіть Go):
```powershell
# Термінал 1
cd go-service
go run ./cmd/server
```
```powershell
# Термінал 2
node blocking-demo.mjs http://localhost:8080 /cpu/sequential
node blocking-demo.mjs http://localhost:8080 /cpu/parallel
```

Скрипт надсилає `/cpu`-запит (без очікування), одразу за ним — кілька `/health` із невеликим
інтервалом, і показує, коли кожен запит пішов (`sentAt`) і коли повернулась відповідь
(`doneAt`). Дивіться на `doneAt`: якщо всі `health#N` завершуються одночасно з `CPU` —
сервер блокується; якщо швидко й незалежно — ні.

### Крок 2. Навантажувальне тестування (RPS, латентність, CPU, RAM)

`scripts/bench-all.mjs` сам піднімає обидва сервери по черзі, б'є по `/io` і `/cpu*` через
[autocannon](https://github.com/mcollina/autocannon), паралельно семплить CPU%/RAM процесу
через [pidusage](https://github.com/soyuka/pidusage) і друкує підсумкову Markdown-таблицю.
Нічого вручну запускати не треба — жодного відкритого термінала з сервером не потрібно.

```powershell
cd scripts
npm install
node bench-all.mjs
```

Корисні параметри (усі опційні, додаються через `--назва=значення`):

| Параметр | За замовч. | Опис |
|---|---|---|
| `--io-connections` | 50 | К-сть паралельних з'єднань для `/io` |
| `--io-duration` | 10 | Тривалість тесту `/io`, с |
| `--io-delay` | 200 | `delayMs` у запитах `/io` |
| `--cpu-connections` | 4 | К-сть паралельних з'єднань для `/cpu*` |
| `--cpu-duration` | 15 | Тривалість тесту `/cpu*`, с |
| `--cpu-timeout` | 30 | Timeout одного `/cpu`-запиту, с |
| `--cpu-iterations` | 300000000 | Ітерацій на один прохід |
| `--cpu-passes` | 4 | К-сть проходів (тільки Go) |

**Чому для `/cpu*` менше з'єднань, ніж для `/io`?** `/io` — це очікування, тому має сенс
перевіряти, скільки паралельних очікувань система тримає одночасно (типовий I/O-бенчмарк:
десятки-сотні з'єднань). `/cpu*` — суто процесорна робота: закидати в неї 50 паралельних
запитів безглуздо, якщо ядер менше — вони просто шикуються в чергу. Конкурентність тут варто
орієнтувати на кількість реальних ядер процесора.

### Крок 3 (опційно). Ручна перевірка в WebStorm

Відкрийте `http-requests/concurrency.http`, виберіть оточення (`node`/`go`) і тисніть ▶ біля
кожного запиту — там уже є `/io`, `/cpu` (Node), `/cpu/sequential` і `/cpu/parallel` (Go), а
також перевірки на 400 та 405.

## 3. Результати

Виміряно на реальній робочій машині (Windows, декілька CPU-ядер — на відміну від одноядерного
контейнера, у якому розроблявся код, тут `/cpu/parallel` вже коректно демонструє прискорення).

### 3.1. Навантажувальне тестування

| Workload | Runtime | RPS | Avg (ms) | p95 (ms) | p99 (ms) | CPU (%) | RAM avg (MB) |
|---|---|---|---|---|---|---|---|
| I/O | Node.js | 240 | 207.8 | 219 | 226 | 0 | 62 |
| CPU | Node.js | 9 | 434.5 | 463 | 541 | 5 | 56 |
| I/O | Go | 245 | 203.7 | 206 | 222 | 0 | 58 |
| CPU (sequential) | Go | 13 | 296.9 | 318 | 320 | 16 | 58 |
| CPU (parallel) | Go | 23 | 177.4 | 215 | 251 | 62 | 59 |

**Висновки:**

- **I/O:** Node (240 RPS) і Go (245 RPS) практично ідентичні — обидві моделі однаково добре
  масштабують конкурентні очікування, просто різними механізмами (event loop проти горутин).
  Латентність (~204-208мс) відповідає заданому `delayMs=200` — вона обмежена самим параметром
  запиту, а не рантаймом.
- **CPU, Node проти Go (sequential):** Go обробляє CPU-навантаження швидше й з більшим RPS
  (13 проти 9), хоча виконує **більший** сумарний обсяг роботи (`300M × 4 = 1.2 млрд` ітерацій
  проти `500M` у Node) — компільований Go в принципі швидший за цикл на V8 для такого коду,
  до того ж Node тут ще й обмежений одним потоком на всі 4 паралельних з'єднання.
- **CPU (sequential) проти CPU (parallel) у Go — головний результат лабораторної:** та сама
  сумарна робота, розподілена по goroutine, дає RPS **13 → 23** (майже вдвічі) і зменшує
  середню латентність **297мс → 177мс**. Водночас завантаження CPU зростає **16% → 62%** —
  тобто паралельна версія справді використовує декілька ядер одночасно, а не лише одне.
  Це саме та поведінка, якої не було видно на одноядерному контейнері: коли ядер кілька,
  розпаралелення через goroutines дає реальний, вимірюваний виграш.
- **RAM:** Go (~58-59MB) і Node (~56-62MB) тут близькі — обидва процеси легкі, істотної
  різниці в пам'яті на цьому навантаженні не видно (на відміну від голого бінарника без
  вхідного трафіку, де Go зазвичай значно легший за Node+V8).

### 3.2. Дослід "спочатку `/cpu`, потім кілька `/health`"

**Node.js**, `/cpu` з дефолтними параметрами (500 000 000 ітерацій, ~227мс):

```
label        sentAt(ms)  doneAt(ms)  duration(ms)  status
CPU                  3         231          227   200
health#1            59         232          173   200
health#2            75         232          157   200
health#3            94         232          138   200
health#4           110         233          122   200
health#5           126         233          107   200
```

Усі п'ять `/health` завершуються **одночасно з CPU-запитом** (232-233мс) — незалежно від
того, коли вони фактично були надіслані (59-126мс). Це прямий доказ: Node **не обробив жодного**
`/health`, поки виконувався `/cpu` — усі відповіді "розморозились" одним пакетом, щойно event
loop звільнився. Класичне повне блокування однопотокового рантайму.

**Go, `/cpu/sequential`** (300M ітерацій × 4 проходи, ~327мс):

```
label        sentAt(ms)  doneAt(ms)  duration(ms)  status
CPU                  4         330          327   200
health#1            63          71            7   200
health#2            86          87            1   200
health#3           102         103            1   200
health#4           118         118            1   200
health#5           138         139            1   200
```

`/health` відповідає за **1-7мс**, хоча `/cpu/sequential` ще виконується майже 330мс — на
багатоядерній машині горутина `/health` одразу отримує вільне ядро, не чекаючи витіснення
важкої горутини.

**Go, `/cpu/parallel`** (та сама робота, 4 goroutines одночасно, лише ~113мс):

```
label        sentAt(ms)  doneAt(ms)  duration(ms)  status
CPU                  4         116          113   200
health#1            58          64            6   200
health#2            74          75            1   200
health#3            99         100            1   200
health#4           115         116            1   200
health#5           133         134            1   200
```

Тут добре видно й другий ефект: сам `/cpu/parallel` завершився за **113мс** — майже втричі
швидше за `/cpu/sequential` (327мс), хоча обчислює той самий сумарний обсяг роботи. Це і є
пряме підтвердження, що 4 проходи реально виконувались одночасно на різних ядрах, а не по
черзі. `/health` при цьому лишається настільки ж швидким (1-6мс), як і в послідовній версії —
вільне ядро для нього знаходиться в будь-якому разі.

## 4. Загальний висновок

| | Node.js | Go |
|---|---|---|
| Модель конкурентності | 1 потік, event loop, non-blocking I/O | Горутини (M:N), плановані по всіх ядрах |
| Поведінка на I/O-навантаженні | Однаково добре масштабується | Однаково добре масштабується |
| Поведінка на CPU-навантаженні | Повністю блокує сервер на час обчислення | Пригальмовує інші запити на мс, не блокує |
| Розпаралелення CPU-роботи "з коробки" | Неможливе без `worker_threads`/кластеризації | `go func()` — і планувальник сам розподіляє по ядрах |
| Вимірюваний ефект розпаралелення (цей тест) | — | RPS 13→23, латентність 297→177мс, час одного запиту 327→113мс |

Головний практичний висновок: якщо сервіс на Node.js має важку CPU-задачу (наприклад,
обробку зображень, парсинг великих файлів, складні обчислення), вона **заблокує обробку всіх
інших запитів**, включно з `/health` — і система оркестрації (Kubernetes, наприклад) може
вважати сервіс "мертвим" через провалений health-check, хоча процес насправді просто зайнятий.
У Go така задача так само займає ресурси, але значно менше заважає обслуговуванню інших
запитів — а якщо задачу свідомо розпаралелити (`go func()` на кожен незалежний шматок роботи),
вона ще й виконається швидше за наявності вільних ядер.
